# apptemplatepy — правила работы

Внутреннее приложение. Его развивают доменные специалисты, не разработчики,
через ИИ-агента. Эти правила обязательны для каждой сессии.

Это **единственный** текст правил проекта. `CLAUDE.md` — указатель на него,
`.cursor/rules/project.mdc` — тоже. Копий нет: две копии расходятся, и через
полгода никто не знает, какая настоящая.

## Контур один, и он боевой

Ветка `main` — это production. Каждый merge в неё уезжает к живым людям с
настоящими данными.

Отдельного контура, где можно ломать бесплатно, нет. Слова «песочница» в этом
проекте тоже нет: оно обещает безопасность, которой не существует.

Что стоит между правкой и живой системой:

1. проверки, которые ты прогоняешь перед коммитом;
2. CI-гейт: красный прогон на контур не попадает;
3. ежедневная резервная копия базы и возможность отката кода.

Третий пункт — уже после аварии. Первые два — до.

## Что этому приложению нужно

`CHECKLIST.md` — источник правды о возможностях приложения. Его ledger
управляет работой:

- строка `absent` — не строй это, пока владелец не попросит;
- строки нет вообще — считается `absent`, спроси;
- строка `removed` — это удаляли сознательно, **не возвращай**.

Мёртвый код, забытая миграция и упоминание в документе — не заказ на фичу.
Увидел расхождение между ledger и кодом — сообщи, не достраивай.

Долговременные решения по проекту пишутся в `CHECKLIST.md` и `docs/`,
а не в этот файл.

## Жёсткие рамки

- Стек только такой. Бэкенд: Python 3.14 + FastAPI + Pydantic + SQLAlchemy
  (async) + Alembic + PostgreSQL. Фронтенд: Vite + React + TypeScript +
  Tailwind + shadcn/ui на Base UI. Никаких других фреймворков, ORM,
  сборщиков и CSS-подходов.
- Новые зависимости ставятся **без согласований**. Но рамки стека выше
  этого права: другой UI-библиотеки, ORM, сборщика или CSS-подхода в
  проекте не появляется. Сначала посмотри, решается ли задача стандартной
  библиотекой или уже установленным.
- Docker в этом проекте не используется. Контур — pm2 и nginx на общем
  сервере, где живут и соседние приложения; один контейнеризованный проект
  посреди них не упростит ничего, а эксплуатацию разведёт надвое.
- Деплой, миграции, работа с сервером и секретами — обычная работа, не
  «чувствительные операции для разработчика». Разработчика в проекте нет.

## Процесс разработки

- **Одна задача — одна сессия.** Не бери в работу несколько несвязанных дел
  подряд: контекст растёт, решения одной задачи протекают в другую, а у
  результата нет чистой точки отката — доставка получается «всё сразу», и
  откатывать приходится нужное вместе с ненужным. Закончил задачу и
  доставил — начинай следующую с чистого листа.
- Любая новая функциональность или изменение поведения начинается с
  проектирования: спека → план → реализация. Не пиши код фичи без
  утверждённого дизайна — даже «простой».
  В Claude Code сессия начинается со скилла `brainstorming` — он и ведёт
  этот порядок; в других агентах тот же порядок руками: сначала письменный
  дизайн и согласие владельца, потом код.

  Скиллы лежат в самом репозитории, `.claude/skills/`, и приезжают вместе с
  ним: `brainstorming` (идея → спека), `writing-plans` (спека → план),
  `executing-plans` (план → код). Раньше здесь было обещание без предмета —
  скилла в шаблоне не было вовсе, и порядок держался на том, что у агента
  случайно окажется свой. Скиллов ровно три, по одному на шаг этого
  порядка: правила про тесты, отладку и интерфейс написаны в этом файле
  своими словами, и вторая их формулировка в скилле разошлась бы с первой.
- Мелкие правки (опечатка, текст на кнопке) — без полного цикла и без
  отдельной сессии, но через обычные проверки перед коммитом.
- Спеки живут в `docs/superpowers/specs/`, планы — в `docs/superpowers/plans/`.
- Образцовая фича — `backend/app/features/expenses/` вместе с экраном
  `frontend/src/routes/expenses.tsx`. Она показывает все паттерны разом:
  роутер, который только проверяет роль и зовёт сервис; схемы Pydantic на
  входе и выходе; сервис с одной транзакцией и записью в журнал аудита;
  деньги целыми копейками; даты в московской зоне; чистый расчёт в
  `app/domain/expenses.py` с unit-тестами; форму, которая разбирает конверт
  ошибки и ставит сообщение под нужное поле; e2e-смоук. Новые фичи строй по
  этому образцу.

## Структура каталогов

- `backend/app/features/<фича>/` — маршруты, правила и таблицы одной фичи.
  Внутри три роли, и они не смешиваются: `router.py` знает только HTTP,
  `service.py` держит правила и транзакцию, `models.py` и `schemas.py` —
  таблицы и формы данных.
- `backend/app/domain/` — чистая логика: расчёты, деньги, даты, агрегации,
  ранги ролей. Без SQLAlchemy, без FastAPI, без I/O. Обязательные
  unit-тесты рядом с кодом.
- `backend/app/core/` — общее для всех фич: конфигурация, сессия базы,
  пароли и токен, зависимости доступа, журнал аудита, конверт ошибки,
  раздача статики.
- `backend/app/core/db.py` — единственная точка доступа к базе в коде
  приложения.
- `backend/app/core/config.py` — единственное место, где читается
  окружение. `os.environ` в модулях `app/` не используется, и обвязка
  (`alembic/env.py`, `backend/tests/conftest.py`) тоже ходит через него, а
  не мимо.

  Единственное исключение — `frontend/playwright.config.ts`: он читает
  `.env` сам, потому что живёт вне Python вовсе. Ему нужен только адрес
  тестовой базы, а конфигурация проверяет весь набор переменных разом, и
  подготовка сервера для сквозных тестов падала бы из-за незаданного
  `APP_AUTH_SECRET`.
- `frontend/src/routes/` — по файлу на экран.
- `frontend/src/components/ui/` — только компоненты shadcn, руками не
  редактируются.
- `frontend/src/components/` (вне `ui/`) — переиспользуемые композиции.
  Данные попадают в них только через пропсы.
- Ширина основного содержимого страницы — только через
  `frontend/src/components/page-main.tsx` (`<PageMain>`), свой `<main>` не
  заводится.
- Отказ сервера показывается, а не проглатывается. Каждый вызов `api`
  проходит через `unwrap` из `frontend/src/api/client.ts`: `queryFn` и
  `mutationFn` обязаны бросать, иначе react-query считает запрос удавшимся,
  а `onSuccess` отрабатывает на неслучившемся изменении. Отказ списочного
  запроса и отказ мутации показываются через
  `frontend/src/components/request-failure.tsx` (`<RequestFailure>`), а не
  пустым состоянием и не молчанием.

  Единственная развилка ПЕРЕД `unwrap` — запрос «кто вошёл» в
  `frontend/src/lib/auth.ts`: 401 там значит «человек не вошёл» и
  превращается в `null`, чтобы роутер показал форму входа. Всё остальное
  бросает, и закрытая часть показывает отказ (`errorComponent` в
  `frontend/src/router.tsx`). Развилка именно на коде 401, а не на пустых
  данных: с `data ?? null` лежащий бэкенд был неотличим от незалогиненного
  человека — владелец набирал верный пароль и снова оказывался на форме
  входа. Сторожит это сквозной сценарий «лежащий бэкенд показывает отказ».
- Ошибка поля формы рисуется под своим полем, общая (`root`) — алертом.
  Список алертов под формой не показывает, к какому вводу относится
  сообщение.
- Гейт по роли (`hasRank`) — это только показ. Спрятанная кнопка ничего не
  защищает: каждый маршрут на бэкенде проверяет роль сам.
- `frontend/src/lib/design/` — темы оформления. Без React и I/O; ввод-вывод
  держит `frontend/scripts/apply-theme.ts`.
- `frontend/src/lib/format.ts` — показ денег и дат. Разбор ввода живёт на
  бэкенде.
- `backend/tests/unit/` — чистая логика, `backend/tests/api/` — маршруты,
  `frontend/tests/e2e/` — сквозной смоук.

### Границы модулей проверяет линтер

`backend/.importlinter` держит три контракта: `domain` не знает ни про базу,
ни про HTTP, ни про фичи; фичи не лезут друг другу внутрь; `router` не
ходит в модели мимо `service`. Нарушение роняет прогон. Понадобилось
обратиться к чужой фиче — это делается через её `service`, и контракт
меняется руками: изменение обязано быть видно в дифе.

## Мутации данных

- Мутации живут в `service.py` фичи. `router.py` только принимает запрос,
  проверяет роль и зовёт сервис.
- Вход разбирается схемой Pydantic, а не чтением полей по месту.
- Ожидаемые ошибки (валидация, отказ по правилу) **не бросаются наружу как
  сбой** — поднимаются как `RuleViolation` и приезжают клиенту единым
  конвертом `{"error": "...", "field": "..."}` со статусом 400. Форма
  ставит сообщение под нужное поле.
- Неожиданные сбои ловит обработчик в `core/errors.py`: наружу уходит
  «Что-то пошло не так», подробности — в лог, который читают через `/logs`.
  Текст исключения наружу не отдаётся никогда: он регулярно содержит кусок
  запроса, путь на диске или адрес базы.
- **Каждая мутация пишет в журнал аудита той же транзакцией**, что и само
  изменение: `write_audit(session, ...)` без commit, а commit делает сервис
  один раз в конце. Отдельный commit для журнала означал бы, что падение
  между двумя коммитами оставляет изменение без следа.
- Проверка роли — зависимостью `require_role` на каждом маршруте, включая
  те, куда интерфейс не ведёт. Ad-hoc проверок нет. Исключений шесть, и они
  двух разных сортов:

  - **Открыты совсем**, ни роли, ни входа: `/api/health` (её зовут доставка
    и монитор, сессии у них нет), `/api/auth/login` (сессию он и выдаёт) и
    `/api/auth/logout` (гасить куку надо и когда она уже недействительна).
  - **Требуют входа, но не роли** (`CurrentUserDep` без `require_role`):
    `/api/auth/me`, `/api/meta/build-info` и `/api/meta/docs/{name}`. Их
    видит любой вошедший, включая `viewer`.

  Путать эти два сорта нельзя: первый доступен любому в интернете, второй —
  только вошедшим.

  Правило держит не только твоя внимательность: `backend/tests/api/`
  `test_route_guards.py` перебирает маршруты приложения по дереву
  зависимостей FastAPI и требует у каждого либо `require_role`, либо
  прописки в одном из двух списков с объяснением. Новый маршрут без защиты
  роняет прогон с именем маршрута в сообщении. До этого теста забытая
  зависимость проходила и ruff, и mypy, и все остальные проверки: это
  значение параметра по умолчанию, а не аргумент декоратора, и в дифе его
  отсутствие не видно.

### Клиентский гейт — не защита

Роутер в браузере уводит на `/login`, когда сессии нет, и прячет пункты
меню не по роли. Это удобство: человек видит форму входа вместо пустого
экрана. Запрос можно послать и мимо интерфейса, поэтому решает всегда
бэкенд. Маршрут без `require_role` открыт всем вошедшим, как бы надёжно его
ни прятал интерфейс.

### Типы клиента генерируются

`frontend/src/api/schema.d.ts` собирается из схемы OpenAPI командой
`make openapi`. Руками не правится. Разошлось с бэкендом — перегенерируй, а
не подгоняй: CI сравнивает файл с заново сгенерированным и падает на любом
дифе.

## База данных

- Схему меняем только через модели SQLAlchemy + `make revision m=<слаг>`,
  затем `make migrate`. Имена как в Alembic: `revision` создаёт, `migrate`
  применяет.
- **Сгенерированную миграцию читают глазами перед применением.**
  `--autogenerate` не видит переименований: он показывает удаление плюс
  добавление, и данные колонки теряются молча. Он не замечает изменения
  состава значений `enum` — добавили роль в `Role`, миграция вышла пустой,
  и приложение падает на первой же записи с новым значением. Он не всегда
  замечает смену типа и никогда — смену смысла.
- Применённые миграции не редактируются — только новая миграция.
- Обратимость проверяется до коммита:
  `alembic upgrade head && alembic downgrade base && alembic upgrade head`.
  Именно этот прогон ловит забытое удаление типа enum в `downgrade`.
- **Деструктивная миграция** (удаление таблицы или колонки с данными) —
  явно предупреди владельца до применения и отметь это в описании
  изменений. Это единственная по-настоящему опасная авария в проекте:
  откат кода её не отменяет, спасает только резервная копия.
- Даты в базе — `TIMESTAMPTZ`. В интерфейсе — через `formatDate` и
  `formatDateTime` из `frontend/src/lib/format.ts` (московская зона).
- Деньги — всегда целые копейки (`amount_minor: int`). Разбор ввода только
  `parse_money_to_minor` из `app/domain/money.py`. Никаких float для денег.
- Колонка `Integer` — это `int4` в PostgreSQL: предел `MAX_AMOUNT_MINOR`,
  примерно 21,47 млн ₽. Сервис, принимающий сумму, обязан проверить её по
  этой константе и вернуть ошибку формы. Без проверки сумма проходит разбор
  и падает в базе ошибкой драйвера, которую специалисту читать нечем.

## Доступ и безопасность

- Роли по рангу: `viewer` < `editor` < `admin`. Ранг считает `has_rank` из
  `app/domain/roles.py` — сравнением строк «больше прав» не выражают.
- Нехватка прав — это 403 с общим конвертом ошибки, а не пустой список и не
  молчание. Отказ попадает в серверный лог, который смотрят через `/logs`;
  в журнал аудита он не пишется — там мутации данных.
- Секреты, пароли и токены никогда не попадают в логи, тексты ошибок и
  e2e-фикстуры. Конфигурация падает через `load_settings`, который печатает
  только имена полей: голый `ValidationError` приложил бы к сообщению весь
  входной словарь вместе с `APP_AUTH_SECRET` и паролем базы.
- Демо-данных и сида в проекте нет. Появятся — создаются только при
  `APP_ENV=local`: на боевом контуре выдуманные записи кто-нибудь примет за
  настоящие.

## Тесты

- Чистая логика в `backend/app/domain/` — обязательные unit-тесты (pytest),
  файл `tests/unit/test_*.py`. Сначала тест, потом код.
- Маршруты — API-тесты в `backend/tests/api/`: коды ответов, форма ошибки,
  отказ по роли, запись в журнал. Каждый тест идёт в своей транзакции и
  откатывается.
- Чистая логика фронтенда (`frontend/src/lib/design/`) — unit-тесты Vitest
  файлом `*.test.ts` рядом с кодом.
- Ключевые пользовательские сценарии — e2e-смоук в `frontend/tests/e2e/`
  (Playwright). При добавлении фичи добавь или обнови смоук её главного
  сценария. E2e-тесты не зависят от сида — данные создаются внутри теста.
- **Unit-тесты на React-компоненты и страницы запрещены** — их роль
  выполняет e2e.

## Интерфейс

1. Компоненты — только shadcn/ui: `npx shadcn@latest add <имя>` или
   композиции из уже установленных примитивов. Другие UI-библиотеки
   запрещены.
2. Если компонент есть в реестре — установи его. Писать самописные аналоги
   кнопок, диалогов, форм и таблиц запрещено.
3. Стили — только Tailwind-классы и токены темы (CSS-переменные из
   `frontend/src/index.css`). Inline-стили и CSS-модули запрещены.
4. Цвета — только семантические токены (`bg-primary`,
   `text-muted-foreground`, `border-border`, `--chart-1…5`). Raw-палитра
   (`text-red-500`), `#hex` и литеральные цветовые функции (`oklch(…)`,
   `rgb(…)`) запрещены. Линтера, который это проверяет, здесь **нет**:
   `make check` зовёт `oxlint`, но тот настроен на правила React и
   TypeScript — про цвета в нём нет ни одного правила. Запрет держится на
   тебе, и нарушение придёт не ошибкой сборки, а тем, что смена темы
   половину экрана не перекрасит.
   Ручные `dark:`-переопределения цветов не нужны: семантические токены
   темизируются сами.
5. Иконки — только `lucide-react`. Графики — только shadcn charts.
6. Примитивы проекта — **Base UI** (`@base-ui/react`, стиль `base-vega`),
   НЕ Radix. Примеры из обучающих данных почти всегда Radix-эпохи, не копируй
   их дословно: `asChild` в Base UI не существует, вместо него проп `render`
   (`<Button render={<a href="…" />}>`). Ссылку, которая должна выглядеть
   кнопкой, через `Button render` не делай: Base UI поверх `render` всё
   равно ставит `role="button"`, и для скринридера это уже не ссылка — сама
   документация Base UI советует не оборачивать так `<a>`. Стилизуй ссылку
   напрямую классами `buttonVariants` из
   `frontend/src/components/ui/button.tsx`
   (`<Link className={buttonVariants({ variant: "outline" })}>`).
   Пункты внутри всплывающих меню всегда оборачивай в группу: `<SelectGroup>`
   в `Select`, `<DropdownMenuGroup>` в выпадающем меню — и когда группа одна,
   и когда их несколько. Без обёртки при раскрытом поддменю края прижимаются;
   выглядит это как поехавшая вёрстка, а не как забытый компонент, поэтому
   причину ищут не там и находят не сразу.
7. Не пиши компоненты shadcn по памяти. Сверяйся с реестром:
   `npx shadcn@latest docs <component>`, `search`, `view`. Индекс
   документации: https://ui.shadcn.com/llms.txt
8. Нужного компонента в реестре нет — сделай композицию из примитивов и
   запиши её в раздел «Разрешённые исключения» ниже.

### Процесс работы над интерфейсом

- Сложные страницы: сначала план — структура страницы и список компонентов
  реестра, потом код.
- Собирай страницы из блоков-секций, а не одним полотном.
- У каждого списка есть пустое состояние. Таблица из одних заголовков
  читается как поломка, и на свежем контуре это первое, что видит человек.
  Одна строка, отличающая «пусто» от «сломано», обязательна.
- Наращивай вертикальными срезами: один роут → его layout → один работающий
  экран → следующий срез.
- После каждого изменения: `make check`, затем проверка в браузере — обе
  темы, мобильная ширина, чистая консоль. Часть ошибок видна только в живом
  браузере.

### Разрешённые исключения

- **Литеральные цвета в `frontend/src/lib/design/themes.ts`.** Правило
  запрещает их в `src/routes/**` и `src/components/**` — там цвет обязан
  быть семантическим токеном. Но сами значения токенов где-то записаны быть
  должны, и это место — определение темы. В разметку они попадают только
  через импорт.
- **Значения токенов в `frontend/src/index.css`** между маркерами
  `theme:start` и `theme:end`. Этот блок пишет `npm run theme`, руками его
  не правят.
- **Inline-стили и `<style>` в
  `frontend/src/routes/design-parts/theme-picker.tsx`.** Образцы цвета на
  карточках и живое превью темы — это данные, а не оформление: класса
  Tailwind с цветом произвольной темы не существует, и выразить их
  правилами нельзя в принципе. Значения приходят импортом из
  `frontend/src/lib/design/`, литералов в разметке нет. Больше нигде в
  `src/routes/**` и `src/components/**` таких стилей быть не должно.
- **Самописная кнопка-карточка там же.** Правило «есть в реестре — ставь
  оттуда» указывало бы на `toggle-group`, но карточка несёт три образца
  цвета, название темы и её имя для команды — это не переключатель, и
  под его API она не ложится. Композиция из примитивов оправдана; если
  карточка станет проще, вернуть `toggle-group`.
- **`frontend/src/components/ui/`** под эти правила не попадает вовсе: файлы
  там генерирует `shadcn`, и руками их не редактируют. Инлайновые стили в
  `chart.tsx` — его код, а не наш.

## Проверки перед любым коммитом

    make check

Он прогоняет обе половины целиком:

| Бэкенд | Фронтенд |
|---|---|
| `ruff format --check` — форматирование | сверка типов клиента со схемой (`check-openapi`) |
| `ruff check` — линтер | `tsc -b --force` — типы |
| `mypy app` — типы | `oxlint` — линтер |
| `lint-imports` — границы модулей | `vitest` — unit-тесты |
| `pytest` — unit- и API-тесты | |

Конвейеры зовут **ту же самую команду** одной строкой, а не пересказывают
этот список своими словами. Это правило, а не случайность: пока `ci.yml` и
`deploy.yml` перечисляли шаги поимённо, они были вторым и третьим списком
одного и того же — и разошлись, потеряв `npm run lint`. Добавляешь проверку
— добавляй её в `Makefile`, и в CI она приедет сама.

Единственное, чего в `make check` нет, — e2e-смоук: ему нужна отдельная база
и браузер, поэтому локально он запускается отдельно
(`cd frontend && npx playwright test`), а в конвейерах стоит своим шагом
следом. Красный прогон останавливает ветку **до** merge, так что `main` не
принимает коммит, который на контур не поедет.

## Доставка

Ветвление: `feature/<слаг>` → проверки → `git merge --no-ff` в `main` →
push → деплой. Один коммит в `main` — одна доставка и одна точка отката.

Доставка только командами. Не изобретай процесс деплоя заново:

| Команда | Что делает | Текст |
|---|---|---|
| `/onboarding` | установка с нуля | `docs/commands/onboarding.md` |
| `/ship` | доставить на контур | `docs/commands/ship.md` |
| `/status` | состояние контура | `docs/commands/status.md` |
| `/logs` | логи контура | `docs/commands/logs.md` |
| `/rollback` | вернуть предыдущую доставку | `docs/commands/rollback.md` |

В Claude Code и Cursor это слэш-команды. В других агентах открой файл из
правой колонки и выполни его шаги.

**Код и данные откатываются по-разному:**

| Что сломалось | Как чиним | Что теряем |
|---|---|---|
| Экран, расчёт, отчёт | `/rollback` — вернуть код и передеплоить | ничего |
| Данные (миграция удалила, синк затёр) | восстановить вчерашний дамп | день работы |

Первый случай — почти всё, что бывает на практике: минуты и без потерь.
Перед восстановлением дампа **обязательно снять дамп испорченного
состояния**, иначе разбирать причину будет не на чем.
