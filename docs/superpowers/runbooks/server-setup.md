# Контур на общем VPS

Сервер один и общий: на нём живут все приложения обоих шаблонов.

## Что уже стоит на сервере

`app-provision`, `app-deprovision`, `app-deploy-key`, `app-secret` в
`/usr/local/bin`. Их исходником владеет `app-template-ts` — здесь копии нет
намеренно: две копии расходятся.

`app-provision <слаг>` заводит базу `<слаг>_prod` и роль `<слаг>_app`,
каталог `/var/www/<слаг>`, `.env` с секретами, `.deploy-env` с портом из
диапазона 3020–3099, два SSH-ключа, vhost в `/etc/nginx/conf.d/`,
сертификат, ночной `pg_dump` (03:17, хранение 14 дней плюс по одной копии на
1-е число), ops-скрипты `<слаг>-status` и `<слаг>-logs` и права `ops` под
них. Для Python-приложения он используется **без правок**: vhost остаётся
чистым `proxy_pass`, потому что статику раздаёт сам FastAPI.

Переменные в том `.env`, что пишет провижинер, — ровно те, которых ждёт
`app/core/config.py`, и лишних там нет: настройки объявлены с
`extra="forbid"`, и посторонняя строка не дала бы контуру подняться.

## Что нужно доставить один раз перед первым Python-приложением

`uv` под пользователем `deploy` — так же, как когда-то Node:

    ssh deploy@<сервер>
    curl -LsSf https://astral.sh/uv/install.sh | sh
    echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
    uv --version

Строка в `~/.bashrc` — только для ручной работы на сервере. Доставке она не
поможет: `ssh host 'bash -s'` поднимает неинтерактивный и не-логин шелл,
который `.bashrc` не читает. Поэтому PATH задан и в самом скрипте доставки —
это не дублирование, а два разных случая.

Node на сервере **не нужен**: фронтенд собирается в GitHub Actions и
приезжает готовой статикой.

## Установка контура

    ssh <слаг>-ops sudo app-provision <слаг>

Через алиас из `~/.ssh/config` (шаг G установки), а не `ssh ops@<адрес>`:
у алиаса свой `IdentityFile`, и обращение по адресу под него не попадает —
ssh уходит с ключом по умолчанию и отвечает `Permission denied` при живом
ключе. У владельца сервера, ставящего контур не из установки, алиаса может и
не быть — тогда ключ задаётся явно: `ssh -i ~/.ssh/<ключ> ops@<сервер> …`.

Скрипт напечатает адрес, порт и публичный ключ для Deploy keys. Дальше:

1. добавить ключ в репозиторий: Settings → Deploy keys (read-only);
2. приватный ключ для Actions забрать конвейером, не показывая на экране:
   `ssh <слаг>-ops sudo app-deploy-key <слаг> | gh secret set DEPLOY_SSH_KEY`
3. `gh secret set SERVER_HOST` — адрес сервера;
4. первый вход — admin / admin. Сменить сразу: контур открыт снаружи, а
   пара известна всем, у кого есть шаблон.

Слаг обязан совпасть с переменной `SLUG` в `.github/workflows/deploy.yml` и
`backup.yml`: им зовутся каталог `/var/www`, процесс pm2, база с ролью,
vhost и каталог резервных копий.

## Чем процесс держится

pm2, а не systemd — потому что вся эксплуатация сервера на нём:
`<слаг>-status` и `<слаг>-logs` зовут `pm2 describe` и `pm2 logs`, права
`ops` выданы под них, автозапуск после ребута идёт через
`pm2-deploy.service`.

Команда запуска веб-процесса, которую ставит доставка:

    pm2 start /var/www/<слаг>/backend/.venv/bin/python --name <слаг> \
      --cwd /var/www/<слаг>/backend \
      -- -m uvicorn app.main:app --host 127.0.0.1 --port <порт>

Uvicorn-воркер у веб-процесса один: счётчики попыток входа живут в памяти
процесса, и второй тихо удвоил бы допустимое число попыток. С воркером
очереди из следующего раздела это разные вещи, названные одним словом: там
«воркер» — отдельный процесс pm2, здесь — рабочий процесс внутри uvicorn.

`pm2 reload` для не-Node процесса — это перезапуск, а не бесшовная замена:
на доставке контур мигает пару секунд. В TS-шаблоне так же.

## Два процесса: веб и воркер очереди

На контуре живут ДВА процесса pm2, и поднимает их обоих доставка:

| Имя в pm2 | Что делает | Что запускает |
|---|---|---|
| `<слаг>` | HTTP: API и статика | `-m uvicorn app.main:app --host 127.0.0.1 --port <порт>` |
| `<слаг>-worker` | очередь фоновых задач: разбор таблиц, обучение модели | `-m app.worker` |

Команда запуска воркера — та же, что у веба, с другим именем и другим
модулем:

    pm2 start /var/www/<слаг>/backend/.venv/bin/python --name <слаг>-worker \
      --cwd /var/www/<слаг>/backend \
      -- -m app.worker

Ставит его доставка, а не `app-provision`: провижинер общий с TS-шаблоном и
используется без правок, о фоновых задачах он не знает и знать не должен.
Побочная выгода — контур, заведённый до появления воркера, получает его сам,
первой же доставкой, без похода на сервер руками.

Порядок в доставке жёсткий: воркер поднимается ПОСЛЕ `alembic upgrade head`
и после веб-процесса. Поднятый раньше миграций, он на первом же обороте
возьмёт задачу и пойдёт в таблицы, которых на старой схеме ещё нет.

Перезагрузку сервера воркер переживает так же, как веб, и по той же причине:
список процессов для `pm2-deploy.service` берётся из `dump.pm2`, а пишет его
`pm2 save` — доставка зовёт его в той же ветке, где впервые запускает
воркера. Без этого воркер пережил бы доставку, но не ребут.

Воркер один. Очередь выдержала бы и нескольких — задача берётся
`SELECT … FOR UPDATE SKIP LOCKED`, и одну задачу получает ровно один
воркер, — но доставка поднимает один процесс: больше на этом контуре не
нужно.

Доставка проверяет, что воркер поднялся, и проверяет НЕ кодом возврата
`pm2 start`: он нулевой и у процесса, умершего на первом импорте, — pm2
просто перезапустит его следом. Проверка смотрит и состояние процесса, и
время его жизни: падающий в цикле тоже бывает `online`, но живёт меньше
паузы перед опросом. В зелёном логе доставки это последняя строка —
`процессы pm2: <слаг> и <слаг>-worker (online)`.

Чего проверка доставки не ловит: воркера, который поднялся и не работает —
например, не достучался до базы (цикл ловит отказы и продолжает). На это
отвечают `/api/jobs/health` и экран «Задачи», а не pm2.

Ни `<слаг>-status`, ни `<слаг>-logs` воркера не показывают: оба зовут pm2 по
одному имени — `<слаг>`. Логи воркера видны только из-под `deploy`:

    PM2_HOME=/home/deploy/.pm2 pm2 logs <слаг>-worker --lines 50 --nostream

Учётке `ops` это не разрешено: в `/etc/sudoers.d/<слаг>-ops` перечислены
ровно `<слаг>-status`, `<слаг>-logs`, `app-deploy-key` и `app-secret`, и
`sudo -u deploy … pm2` отвечает «not allowed to execute». Значит, у
специалиста про воркера есть два источника — лог доставки и экран «Задачи»;
всё остальное — к владельцу сервера.

На своей машине воркер запускают вторым терминалом:

    cd backend && uv run python -m app.worker

## Известное расхождение

`<слаг>-status` проверяет корень, а не `/api/health`. Для SPA корень
отдаёт `index.html` с кодом 200 даже при недоступной базе, то есть скрипт
подтверждает меньше, чем кажется. Настоящую проверку делает доставка. Чтобы
исправить, пришлось бы менять общий провижинер — это решение сразу для двух
шаблонов.

Пока оно не принято, расхождение закрыто на стороне команды: `/status` сам
ходит `curl` по `https://<адрес>/api/health` отдельным шагом и живость
считает по нему, а не по коду серверного скрипта. Раньше расхождение было
только записано здесь — а команда продолжала рапортовать «контур жив» при
лежащей базе.

Второе расхождение того же рода — воркер: `<слаг>-status` и `<слаг>-logs`
его не видят вовсе (раздел «Два процесса»). Причина та же, общий провижинер,
и закрыто оно там же, в `/status`: шаг про воркера ходит за состоянием в лог
доставки и на экран «Задачи».
