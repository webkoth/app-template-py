# app-template-py — дизайн ядра

Дата: 2026-08-31. Статус: утверждено владельцем, план не написан.

## Задача

Второй стартовый шаблон внутреннего приложения — для тех, кто предпочитает
Python, и для задач, где бэкенд на Python объективно уместнее: табличные
расчёты, классическое ML, работа с внешними моделями по API.

Это **не переезд** с `app-template-ts` и не его замена. Оба шаблона живут
дальше, каждый со своим репозиторием и своей установкой. Владелец выбирает
шаблон под задачу до начала работы.

Эта спека покрывает **ядро**: рабочее приложение со входом, ролями, аудитом,
образцовой фичей, боевым контуром и доставкой. Слой данных (загрузка файлов,
очередь с воркером, pandas, scikit-learn, клиент внешних моделей) утверждён
владельцем и приезжает **отдельной спекой**, поверх готового ядра.

## Отношение к app-template-ts

Что остаётся общим — не ради красоты, а потому что это уже работает и
проверено на живом сервере:

- модель контура: `main` = production, песочницы нет;
- `AGENTS.md` как единственный источник правил, `CLAUDE.md` и
  `.cursor/rules/project.mdc` — указатели на него;
- `CHECKLIST.md` с ledger возможностей и его семантикой
  `included` / `available` / `absent` / `removed`;
- команды `/onboarding`, `/ship`, `/status`, `/logs`, `/rollback` с текстами
  в `docs/commands/`;
- общий VPS 161.104.50.20 и **тот же самый** `app-provision <слаг>`;
- внешний вид: Tailwind, shadcn/ui в стиле `base-vega` на Base UI, иконки
  lucide, пять тем оформления, витрина `/design`;
- языковые конвенции: интерфейс по-русски, код по-английски, conventional
  commits с русским описанием.

Что расходится и почему — раздел «Правила: дельта к app-template-ts».

## Принятые решения

Решения приняты владельцем в ходе проектирования; здесь они зафиксированы
вместе с причиной, чтобы следующая сессия не пересматривала их заново.

1. **Фронтенд — SPA на Vite, а не Next.js и не Jinja/HTMX.**
   Next.js оставил бы в бою второй процесс на Node — ровно то, от чего
   уходит человек, выбравший Python-шаблон, — и заставил бы описывать один
   контракт дважды, в Pydantic и в Zod. Jinja с HTMX выбросил бы shadcn/ui,
   а вместе с ним весь раздел правил про интерфейс, который держит планку
   качества. Vite даёт статику: в рантайме остаётся один Python-процесс,
   Node нужен только на сборке.

2. **Раскладка бэкенда — по фичам, слои внутри фичи.**
   Изменения в таком приложении приходят фичами («добавить поле в расходы»,
   «расходы требуют согласования»), а не слоями: в раскладке по фичам это
   один каталог, в слоистой — четыре, и один из четырёх забывают. Слоистая
   раскладка вдобавок не задаёт границ между фичами вовсе — только между
   техническими уровнями, — и через полгода сервисы ходят в чужие
   репозитории напрямую. Границы по фичам можно проверять линтером, и мы их
   проверяем.

3. **Локальных нейросетей в шаблоне нет.**
   `torch` с моделью — это 2,5–3 ГБ зависимостей плюс память под инференс.
   Провижинер требует 4 ГБ свободного места на весь контур; общий VPS такое
   не держит. Внешние модели по HTTP — да, спекой 2.

4. **Docker не используется.**
   Названо явно, потому что в Python-мире контейнер — ожидание по умолчанию.
   Контур на этом VPS — pm2 и nginx, общий для всех приложений сервера. Один
   контейнеризованный проект посреди них ничего не упростит, а ops-модель
   разведёт надвое.

## Бэкенд: слои и границы

Внутри каждой фичи три роли, и они не смешиваются:

- `router.py` — только HTTP: разбор запроса, зависимости доступа, коды
  ответов. Ни правил, ни запросов к базе.
- `service.py` — правила и транзакция. Здесь же запись в аудит.
- `models.py` — таблицы SQLAlchemy. `schemas.py` — модели Pydantic для
  входа и выхода.

`app/domain/` — чистая логика без React, без базы, без сети: разбор и
проверка денег, даты в московской зоне, категории и агрегации расходов,
ранги ролей. Обязательные unit-тесты рядом с кодом.

Границы проверяются `import-linter` в составе `make check`, а не
договорённостью. Контракты:

1. `app.domain` не импортирует ни `app.core`, ни `app.features`.
2. `app.features.*` не импортируют внутренности друг друга: обращение к
   чужой фиче идёт только через её `service`.
3. `router` не импортирует `models` — только `service` и `schemas`.

Нарушение роняет прогон. Архитектура, которую проверяет прогон, переживает
год работы; архитектура из договорённостей — нет.

## Схема данных

Три таблицы, имена колонок совпадают с эталоном: `users`, `audit_log`,
`expenses`.

- **Идентификаторы** — `uuid7()` из stdlib 3.14, тип в базе родной `uuid`.
  Не `cuid`, как в эталоне: в Python он потребовал бы зависимость, а UUIDv7
  упорядочен по времени и не разносит B-tree по страницам так, как UUIDv4.
- **Даты** — `TIMESTAMPTZ(3)`. Показ — московская зона, форматирование на
  фронтенде.
- **Деньги** — целые копейки в `Integer`. Предел `MAX_AMOUNT_MINOR` =
  2 147 483 647 остаётся тем же: это предел `int4` в PostgreSQL, а не
  особенность языка. Сервис, принимающий сумму, обязан проверить её по этой
  константе и вернуть ошибку — иначе сумма пройдёт разбор и упадёт ошибкой
  драйвера, которую читать нечем.
- **`users`** — `login` уникален, `password_hash` допускает NULL (вход
  невозможен), `status` = `active` | `disabled`, `sessions_valid_from`
  отзывает выданные сессии. Удаления пользователей нет намеренно: удалённый
  автор записи в журнале превратил бы историю в осиротевшие строки.
- **`audit_log`** — `actor` строкой, а не связью с `users`: журнал обязан
  пережить учётную запись. Тот же известный долг, что в эталоне: появится
  переименование логинов — журнал разойдётся с реальностью.
- **`expenses`** — образцовая таблица, удаляется вместе с образцовой фичей.

Миграции — только через Alembic. Сгенерированная `--autogenerate` миграция
**читается глазами перед применением**: autogenerate не видит переименований
(показывает удаление плюс добавление) и молча теряет данные колонки.
Применённые миграции не редактируются — только новая. Деструктивная миграция
требует явного предупреждения владельцу до применения.

## Авторизация и доступ

Схема переносится из эталона целиком, вплоть до формата хранения.

- **Пароли** — `hashlib.scrypt` из stdlib, формат строки
  `scrypt$<N>$<salt_hex>$<hash_hex>`, параметры те же. Побочный эффект:
  хэши совместимы между шаблонами, базу с пользователями можно перенести из
  TS-приложения без сброса паролей.
- **Токен сессии** — HMAC-SHA256 поверх логина и времени выдачи, сверка
  через `hmac.compare_digest`. Кука та же по имени и атрибутам;
  `COOKIE_SECURE` обязателен при `APP_ENV=production`.
- **Проверка сессии** — роль и статус читаются из базы на каждом запросе,
  поэтому смена роли и отключение учётной записи действуют немедленно.
  Сессии, выданные раньше `sessions_valid_from`, недействительны: подпись у
  отозванной куки остаётся верной, поэтому проверка обязана быть здесь.
- **Ограничение попыток входа** — по логину и по адресу из `X-Real-IP`
  (nginx отдаёт адрес сокета, а не цепочку `X-Forwarded-For`, первый сегмент
  которой подконтролен клиенту). Счётчики в памяти процесса — известный
  долг, унаследованный от эталона; поэтому воркер один.
- **Время отказа выровнено**: несуществующий логин и неверный пароль
  отвечают за одинаковое время.
- **Роли** — `viewer` < `editor` < `admin`, сравнение по рангу. Неизвестная
  роль означает отказ, а не пропуск: ошибка настройки обязана закрывать
  доступ, а не открывать.
- **Первая учётная запись** — `APP_BOOTSTRAP_*`, пара по умолчанию
  admin / admin, заводится только при пустой таблице. Пустое значение любой
  из переменных выключает bootstrap. Предупреждение висит на первом экране,
  пока вход идёт под дефолтной парой.

**Каждый роутер проверяет роль сам** через зависимость `require_role`,
включая маршруты, куда интерфейс не ведёт. Клиентский гейт — удобство, а не
защита. Отказ по правам пишется в серверный лог и виден через `/logs`.

## Контракт API

- `GET /api/health` — короткий запрос в базу и 200, если контур жив. Им
  пользуется health-check доставки. Совсем без авторизации живут три
  маршрута: он, вход и выход (вход выдаёт сессию, а гасить куку надо и
  тогда, когда она уже недействительна). Список закреплён тестом
  `backend/tests/api/test_route_guards.py`, и пополнять его — решение, а не
  формальность.
- Префикс `/api`. Версий в путях нет: клиент и сервер живут в одном
  репозитории и уезжают одним коммитом, версионировать контракт с самим
  собой — церемония без содержания.
- **Единый конверт ошибки**: `{"error": "текст", "field": "amount"}`.
  Статус 400 для нарушения правил; ответ Pydantic на невалидный ввод
  приводится к тому же виду обработчиком в `core/errors.py`. Без этого на
  клиенте появятся две ветки разбора ошибок, и вторая будет написана хуже.
  `field` необязателен: без него форма показывает текст общим алертом.
- Ожидаемые ошибки возвращаются, а не бросаются — та же философия, что у
  `FormState` в эталоне. Бросаются только настоящие сбои; их ловит
  обработчик, пишет в лог и отдаёт 500 без подробностей наружу.
- **Аудит пишется в той же транзакции, что и мутация.** В эталоне
  `writeAudit` вызывается отдельно после записи: падение процесса между
  ними оставило бы изменение без следа. Журнал с дырами доверия не
  заслуживает.
- Типы клиента генерируются из OpenAPI:
  `uv run python -m app.openapi > openapi.json`, затем
  `openapi-typescript` в `frontend/src/api/schema.d.ts`. Файл руками не
  правится. CI перегенерирует его и падает при любом дифе — «бэкенд поменял
  контракт, фронт не заметил» становится красным прогоном на ветке.

## Фронтенд

- Маршруты: `/login`, `/` (лендинг), `/expenses`, `/users`, `/audit`,
  `/design`, `/docs`.
- Данные — TanStack Query. Формы — react-hook-form с zod: проверка в
  браузере мгновенная, но решает всегда сервер, потому что запрос можно
  послать и мимо формы.
- Проблема эталона с возвратом введённого (`values` в `FormState`,
  `key` на полях, эхо даты в тексте ошибки) здесь исчезает: состояние формы
  живёт на клиенте и после ответа сервера никуда не девается.
- Ширина основного содержимого — только через общий компонент `PageMain`.
- Компоненты — только shadcn/ui или композиции из установленных примитивов.
  Цвета — только семантические токены; запрет raw-палитры и литеральных
  цветов проверяется линтером, как в эталоне.
- У каждого списка есть пустое состояние.
- Темы оформления, `npm run theme -- <имя>` и витрина `/design` переносятся
  как есть: темы — это CSS-переменные в `globals.css`, к бэкенду отношения
  не имеют, и переписывать их на Python было бы вредительством.
- `/docs` показывает те же документы, но берёт их не с диска фронтенда, а
  через `features/meta/router.py`, который читает `AGENTS.md` и
  `docs/commands/*` из репозитория на сервере. Поведение для человека
  прежнее.

### Где живут деньги и даты

Граница, которой в эталоне не было и которую надо провести явно, иначе одно
правило окажется в двух местах.

**Бэкенд владеет разбором.** `parse_money_to_minor("12,34") → 1234`,
проверка предела, разбор даты с отсевом «2026-02-31». Это решает, что
попадёт в базу, значит должно быть авторитетным и не зависеть от клиента.

**Фронтенд владеет показом.** `formatMoney` и `formatDate` через `Intl` с
московской зоной — один файл, из которого форматируют и таблица, и подпись
на графике. API отдаёт сырое: `amount_minor` числом, дату в ISO с зоной.
Иначе сортировка, фильтры и графики упрутся в строки, которые нечем
сравнивать.

Оговорка: форматирование денег появляется и на бэкенде — в текстах его
собственных ошибок («Сумма больше предельной (21 474 836,47 ₽)»). Это два
коротких форматтера вместо одного, оба под тестами. Худшее расхождение между
ними — неразрывный пробел вместо обычного: расхождение в разборе стоило бы
денег, расхождение в показе стоит косметики.

## Контур и провижининг

он заводит базу и роль, каталог `/var/www/<слаг>`, `.env` с секретами,
`.deploy-env` с портом из диапазона 3020–3099, два SSH-ключа, vhost в
`/etc/nginx/conf.d/`, сертификат, ночной `pg_dump` с хранением 14 дней плюс
по одной копии на 1-е число, ops-скрипты и права `ops`.

Провижинер остаётся нетронутым потому, что раздача статики идёт через
FastAPI: vhost — по-прежнему чистый `proxy_pass` на порт. Вариант с раздачей
через nginx быстрее, но потребовал бы своего vhost, то есть правки общего
провижинера, которым уже пользуется TS-шаблон. Для внутреннего приложения
экономия миллисекунд на отдаче трёх файлов этого не стоит; если однажды
упрёмся — это правка одного `server`-блока, а не переделка.

Единственное новое требование к серверу — установленный `uv`. Ставится
один раз, как когда-то Node; строка в
`docs/superpowers/runbooks/server-setup.md`, не в провижинере.

**Своей копии `scripts/server/` в этом шаблоне нет.** Провижинер установлен
на сервере как `/usr/local/bin/app-provision`, а исходником владеет
`app-template-ts`. Копия здесь означала бы два одинаковых скрипта в двух
репозиториях — ровно то, что правила запрещают в тексте про `AGENTS.md`:
две копии расходятся, и через полгода никто не знает, какая настоящая.
Цена решения названа честно: `app-template-py` зависит от чужого
репозитория в части провижининга. Понадобится провижинеру разойтись по
языкам — он переезжает в собственный репозиторий, общий для обоих шаблонов,
и это отдельное решение владельца, а не побочный эффект правки.

Процесс держит **pm2**, а не systemd:

```
pm2 start .venv/bin/python --name <слаг> --cwd /var/www/<слаг>/backend \
  -- -m uvicorn app.main:app --host 127.0.0.1 --port $PORT
```

Причина не в том, что pm2 лучше для Python, а в том, что вся эксплуатация
сервера на нём: `<слаг>-status` и `<слаг>-logs` зовут `pm2 describe` и
`pm2 logs`, права `ops` выданы под них, автозапуск после ребута идёт через
`pm2-deploy.service`. Уход на systemd развёл бы ops-скрипты, sudo-правила и
голову человека, чинящего контур ночью.

Цена названа явно: `pm2 reload` для не-Node процесса — перезапуск, а не
бесшовная замена, и на доставке контур мигает пару секунд. В эталоне так же
(Next тоже в fork-режиме), то есть это паритет, а не регресс.

Воркер один. Счётчики попыток входа живут в памяти процесса, и второй воркер
тихо удвоил бы допустимое число попыток. Вопрос о нескольких процессах
встанет вместе с очередью в спеке 2 и решается там же, общим хранилищем
счётчиков.

## Доставка и CI

Расхождение с эталоном одно, зато принципиальное: **фронтенд собирается в
GitHub Actions, а не на сервере.** Так на сервере не оказывается ни Node, ни
`node_modules`: человек, выбравший Python-шаблон, не обнаруживает в бою
вторую экосистему. Побочно это ускоряет доставку и снимает с сервера самый
прожорливый шаг.

`ci.yml` — на любой ветке кроме `main` и на pull request, с сервисом
PostgreSQL 18:

```
uv sync --frozen
ruff format --check · ruff check · mypy · lint-imports
alembic upgrade head
pytest
npm ci · tsc --noEmit · проверка дрейфа сгенерированных типов
vite build
playwright test
```

`deploy.yml` — на push в `main`: те же проверки, затем job доставки с
`concurrency: deploy`:

```
ssh deploy@<сервер>:
  git fetch origin main && git reset --hard origin/main
  uv sync --frozen
  uv run alembic upgrade head
  ← распаковка dist, собранного в Actions
  pm2 reload | pm2 start (первый раз)
  health-check: 200 на http://127.0.0.1:$PORT/api/health
```

Первый деплой разворачивает репозиторий на месте (`git init` + `remote add`
+ `reset --hard`), а не клонирует: каталог уже не пуст — провижинер положил
туда `.env` и `.deploy-env`, а `git clone` в непустой каталог отказывается.
Файлы окружения при этом целы: `reset --hard` не трогает неотслеживаемое.
Это грабли, найденные на живом сервере при проверке эталона, и повторять их
незачем.

Health-check доставки бьёт в `/api/health`, а не в корень. В эталоне корень отвечал
307 — переброс на форму входа, — и проверка это учитывала. Здесь корень
всегда отдаёт `index.html` с кодом 200, потому что решение о входе принимает
роутер уже в браузере: проверка корня подтверждала бы только то, что nginx
жив и файл на месте, даже когда база недоступна и приложение нерабочее.
`/api/health` открыт без авторизации, ходит в базу коротким запросом и
отвечает 200 только когда контур действительно жив.

Оговорка про `<слаг>-status`: этот скрипт пишет провижинер, а провижинер мы
не трогаем, — значит он продолжит проверять корень и показывать 200 даже
при недоступной базе. Расхождение осознанное: доставка, которая одна и
решает, пускать ли изменение на контур, проверяет по-настоящему, а ops-скрипт
остаётся общим для обоих шаблонов. Понадобится и ему настоящая проверка —
это правка провижинера, то есть общее решение для двух шаблонов сразу.

`backup.yml` — ежедневная проверка свежести ночной копии, переносится как
есть.

`/rollback` работает без изменений: `git revert` и пуш запускают обычную
доставку, которая пересобирает фронтенд на откаченном состоянии. Ничего
специального для артефактов не нужно.

## Проверки

Toolchain два, точка входа одна — иначе половину проверок будут забывать.

```
make check     ruff format --check · ruff check · mypy · lint-imports · pytest
               tsc --noEmit · проверка дрейфа типов · vitest
make dev       бэкенд и фронтенд разом
make revision  alembic revision --autogenerate, затем чтение глазами
make migrate   alembic upgrade head
```

`make check` прогоняется перед любым коммитом. Его же прогоняет CI на
feature-ветке вместе с e2e, которому нужна отдельная база и который поэтому
локально запускать не обязательно. Красный прогон останавливает ветку до
merge.

Рассматривался `just` — приятнее синтаксисом, но это ещё один инструмент на
каждую машину. `make` есть везде.

## Тесты

- Чистая логика в `app/domain/` — обязательные unit-тесты (pytest), сначала
  тест, потом код.
- API-тесты на httpx через ASGI-транспорт: доступ по ролям, конверт ошибки,
  запись в аудит, отзыв сессии. Это уровень, которого в эталоне не было
  вовсе (там его роль играли e2e), и он дешевле e2e на порядок.
- Ключевые сквозные сценарии — Playwright в `frontend/tests/e2e/`. Тесты не
  зависят от сида: данные создаются внутри теста.
- Unit-тесты на React-компоненты запрещены — их роль выполняет e2e.

## Правила: дельта к app-template-ts

`AGENTS.md` сохраняет структуру и большую часть текста эталона. Слово в
слово переезжают: «контур один, и он боевой»; ledger как источник правды о
возможностях; процесс «спека → план → реализация»; весь раздел про интерфейс
с Base UI, `render` вместо `asChild` и группами в выпадающих меню; языковые
конвенции; доставка только командами; разница между откатом кода и
восстановлением данных.

**Переписываются:**

- Жёсткие рамки стека — на Python-версию, с тем же запретом на
  альтернативные ORM, фреймворки, сборщики и CSS-подходы.
- Структура каталогов — `features/`, `domain/`, `core/` и контракты
  import-linter вместе с объяснением, зачем они.
- Мутации данных — вместо server actions с `FormState`: роутер знает только
  HTTP, правила и транзакция живут в сервисе, аудит идёт той же
  транзакцией, ожидаемая ошибка возвращается конвертом.
- Окружение — `Settings` на pydantic-settings как единственное место чтения
  env в коде приложения; исключения для обвязки (Alembic, скрипты) описаны
  так же явно, как в эталоне.
- База данных — Alembic вместо Prisma, включая правило про чтение
  сгенерированной миграции.

**Появляются три новых пункта**, каждый закрывает ошибку, которой в эталоне
не могло быть:

1. Клиентский гейт маршрутов — удобство, а не защита. Каждый роутер
   проверяет роль сам, включая маршруты, куда интерфейс не ведёт.
2. `frontend/src/api/schema.d.ts` генерируется и руками не правится.
   Разошлось — перегенерируй, а не подгоняй.
3. Миграции Alembic читаются глазами перед применением.

## Ledger

Строки эталона переносятся с теми же состояниями: вход по логину и паролю,
первая учётная запись из переменных, роли, отключение учётной записи, журнал
аудита, образцовый раздел «Расходы», стартовая страница, `/design`, темы,
`/docs`, ежедневная копия базы — `included`. Смена пароля в приложении,
отслеживание ошибок внешним сервисом, платежи, задачи по расписанию,
почтовые уведомления — `absent`.

Возможности слоя данных (загрузка файлов, очередь и воркер, расчёты на
pandas, scikit-learn, клиент внешних моделей) получают состояние `absent` с
примечанием, что они **утверждены владельцем и приедут отдельной спекой**.
Так следующая сессия отличит «этого нет и не просили» от «этого ещё нет».

Известный технический долг переносится: счётчики попыток входа в памяти
процесса; `audit_log.actor` — логин строкой, без связи с `users`.

## Допущения

- Приложение внутреннее, за формой входа целиком. SEO не нужен, поэтому
  отсутствие серверного рендеринга ничего не стоит.
- Пользователей десятки, не тысячи. Один воркер uvicorn покрывает нагрузку
  с запасом.
- На сервере есть `uv`; если нет — это шаг установки, а не сбой.
- Владелец выбирает между шаблонами до старта проекта; смены шаблона на
  ходу не предусмотрено.

## Что осознанно не делаем

- **Docker** — контур на этом VPS pm2 и nginx, общий для всех приложений.
- **Локальные нейросети (`torch`)** — не встают на общий сервер.
- **Версии в путях API** — клиент и сервер уезжают одним коммитом.
- **Смена пароля в приложении** — как в эталоне: заводят новую учётную
  запись и отключают старую.
- **Несколько воркеров uvicorn** — до общего хранилища счётчиков попыток.
- **Отдельный контур для экспериментов** — модель контура одна и боевая.
- **Серверный рендеринг и SSR-фреймворки** — см. решение 1.

## Что приедет спекой 2

Загрузка файлов и их хранение; очередь и воркер; долгие расчёты с прогрессом
и экраном состояния задач; pandas и scikit-learn с хранением обученных
моделей; клиент внешних моделей в `lib/integrations/` с режимами
mock/fixture; образцовая фича «загрузили таблицу → посчитали в фоне →
показали результат», заменяющая «Расходы».

Ядро проектируется с оглядкой на этот слой: доступ к базе async, границы
фич проверяются линтером, шов под воркер и под хранилище файлов оставлен
свободным — чтобы второй слой пришёлся по месту, а не через переписывание.
