# /rollback — вернуть предыдущую доставку

**Сначала пойми, что именно сломалось.** Это две разные аварии:

| Что сломалось | Чем чинить |
|---|---|
| Экран, расчёт, отчёт | откат кода — эта команда |
| Данные (миграция удалила колонку, синк затёр) | восстановление копии, эта команда НЕ поможет |

Откат кода не отменяет миграцию: если колонку удалили, её нет и после
отката, а старый код на такой базе не поднимется. Если авария про данные —
остановись и скажи: нужен дамп с сервера, каталог
`/home/deploy/backups/<слаг>/`, и **перед восстановлением обязательно снять
дамп испорченного состояния**, иначе разбирать причину будет не на чем.

## Порядок

1. `git fetch origin` и покажи последние доставки:
   `git log origin/main --merges --oneline -10`
   Точка отката по умолчанию — последний merge-коммит. Если аргументом дан
   коммит, считай точкой его.
2. Покажи, что уйдёт, и спроси подтверждение. Отдельно проверь миграции:
   `git diff <точка-отката>..origin/main --stat -- backend/alembic/versions/`
   Миграции в списке — откат кода их не отменит, и **файлы ревизий из отката
   надо исключить**; как именно, сказано в шаге 3.
3. Откат — **возвратом изменений, а не переписыванием истории**:
   ```
   git switch main
   git pull origin main
   git revert --no-commit -m 1 <merge-коммит>
   git commit -m "revert: откат доставки <коммит>"
   git push origin main
   ```
   Форс-пуш в `main` запрещён: на репозитории параллельно работают
   несколько копий, и переписанная история ломает их все. Возврат даёт то же
   состояние контура и никого не ломает.

   **Если в шаге 2 нашлись миграции — на одну команду больше:**
   ```
   git revert --no-commit -m 1 <merge-коммит>
   git checkout <merge-коммит> -- backend/alembic/versions/
   git commit -m "revert: откат доставки <коммит> (миграции оставлены)"
   ```
   Файлы ревизий возвращаются на место намеренно. База уже переведена на
   новую ревизию, и откат кода её назад не переводит; а доставка на шаге
   `alembic upgrade head` читает историю миграций из ДЕРЕВА. Ревизии, на
   которой стоит база, в откаченном дереве нет — alembic падает с
   `Can't locate revision identified by <ревизия>` и кодом 255, а `set -euo
   pipefail` роняет весь шаг. Воспроизведено на живой базе.

   Падает он в самой середине: `git reset --hard` уже прошёл, статика уже
   подменена на старую, `uv sync` уже привёл `.venv` к старому набору
   зависимостей, а `pm2 reload` ещё не выполнялся — то есть на контуре
   остаётся старая статика, процесс со старым кодом В ПАМЯТИ и новая схема
   базы. С оставленными файлами миграций `alembic upgrade head` не делает
   ничего (база и так на head), доставка доходит до конца, и на контуре
   оказывается старый код на новой схеме — рабочее состояние, пока миграция
   была добавляющей.

   Если доставка уже развалилась посередине — чинится тем же: доложи
   исправленный откат (с оставленными миграциями) и дождись прогона. Шаги
   доставки идемпотентны, повторный проход приводит контур в порядок целиком.
   Руками на сервер лезть не надо, да и нечем: ключ `ops` умеет только
   `<слаг>-status` и `<слаг>-logs`.
4. Дождись доставки: `sh scripts/wait-for-run.sh deploy.yml`
   Скрипт ждёт прогон именно за коммитом отката. Прежняя подстановка
   `gh run list --branch main -L1` в окне между push и созданием прогона
   отдавала ПРОШЛЫЙ прогон — тот самый, который и привёз аварию, — и откат
   объявлялся доехавшим, пока он ещё шёл.
5. Проверь живость и скажи пользователю, на каком коммите теперь контур.
6. Причину поломки чини **на новой ветке от `main`, начав её с возврата
   возврата**:
   ```
   git switch main
   git pull origin main
   git switch -c feature/<слаг>-возврат
   git revert --no-edit <коммит-отката>
   ```
   Первая команда возвращает фичу в ветку, дальше в ней чинится причина, и
   доставка идёт обычным `/ship`.

   Порядок именно такой, и это не церемония. После `git revert -m 1` git
   по-прежнему считает feature-ветку слитой: `git merge --no-ff` в `/ship`
   принесёт из неё только НОВЫЕ коммиты, а самой фичи в `main` не появится.
   Прогон при этом зелёный, доставка зелёная, а кода фичи на контуре нет.
   Воспроизведено: починка на старой ветке довезла до `main` файл
   исправления и не довезла файл фичи.

   Возврат возврата делается на ветке, а не в `main`: в `main` он вернул бы
   сломанную фичу на контур немедленно — тем же push, до всякой починки.
   На ветке от `main` он ложится чисто (фичи там нет), а на контур уезжает
   уже вместе с исправлением, одной доставкой.
