# /onboarding — установка приложения из шаблона

Проведи установку от клонированного шаблона до работающего боевого контура.
Иди по шагам, после каждого блока коротко сообщай статус. Если шаг уже
выполнен — проверь и иди дальше. При ошибке установки разберись сам, не
бросай пользователя с сырой командой.

Говори по-русски. Пользователь — доменный специалист, не разработчик:
объясняй продуктовым языком, техническую глубину добавляй только там, где
без неё не принять решение.

## A. Знакомство

Спроси: имя и фамилию (для авторства коммитов), рабочий email, название
приложения и слаг (латиница в нижнем регистре, цифры и дефис — им будут
названы база, процесс и адрес).

## B. Проверка окружения

Проверь и поставь недостающее:

- `git`, `gh`
- `uv` (он же принесёт Python 3.14): `curl -LsSf https://astral.sh/uv/install.sh | sh`
- Node.js 24 — только для сборки фронтенда; в бою его нет
- PostgreSQL 18

По системам:

- **macOS:** `brew install git node gh postgresql@18 && brew services start postgresql@18`,
  затем `uv` командой выше.
- **Linux (Ubuntu/Debian):** git и gh из apt (gh — репозиторий
  cli.github.com), Node 24 — NodeSource, PostgreSQL 18 — PGDG, `uv` командой
  выше.
- **Windows (PowerShell):**
  `winget install --silent Git.Git OpenJS.NodeJS GitHub.cli PostgreSQL.PostgreSQL.18 astral-sh.uv`
  После установки PostgreSQL спроси пароль суперпользователя `postgres`,
  который пользователь задал установщику. Перезапусти терминал, проверь
  версии. Отдельно проверь `make --version`: весь проект ходит через
  `Makefile`, а GNU Make в Windows не входит — он приезжает с Git Bash или
  MSYS2. Без него команды `make install`, `make migrate`, `make dev` и
  `make check` не запустятся.

Затем `gh auth login` (HTTPS, авторизация через браузер) и
`git config --global user.name` / `user.email` из шага A.

Готовность показывает `node scripts/onboarding-check.mjs`.

**Про первый `make check` на macOS.** Он поставит `import-linter`, а тот тянет
`grimp`, у которого нет готового колеса под Python 3.14 на macOS: под обычный
интерпретатор колёс нет, есть только под free-threaded сборку. Установка
скачает тулчейн Rust и соберёт расширение — это порядка двадцати минут, один
раз на машину. Команда в этот момент выглядит зависшей, но она работает; не
прерывай её. Результат кэшируется, повторные запуски мгновенные. На Linux и в
CI колесо есть, и ничего этого не происходит.

## C. Анкета

Заполни `CHECKLIST.md` вопросами из него, по-русски и продуктовым языком.
Разделы «Приложение» и «Первая версия» обязательны до любой работы над
кодом. Состояние установки переведи в `идёт`.

Ничего из раздела «Решает агент» у пользователя не спрашивай.

## D. Переименование

**Не делай глобальную замену.** Сначала инвентаризация:

`rg -n "apptemplatepy|app-template"`

Затем правь каждый владеющий источник по отдельности:

| Что | Где |
|---|---|
| имя пакета бэкенда | `backend/pyproject.toml`, поле `name`. Затем `cd backend && uv lock` — имя подтянется в `uv.lock` само, руками lock не правят |
| заголовок схемы OpenAPI | `backend/app/main.py`, `title=`. В типы клиента он не попадает, `make openapi` после этого не нужен |
| имя базы, роль и пароль | `.env.example` — обе строки, `DATABASE_URL` и `DATABASE_URL_E2E` |
| имена баз в конвейерах | `.github/workflows/deploy.yml` и `ci.yml` — `POSTGRES_DB`, обе переменные `DATABASE_URL*` и `CREATE DATABASE` |
| слаг контура | `.github/workflows/deploy.yml` и `backup.yml` — переменная `SLUG`. Им же зовутся каталог `/var/www`, процесс pm2, база с ролью, vhost и каталог резервных копий; он обязан совпасть со слагом, с которым будет вызван `app-provision` на шаге H |
| заголовки | `AGENTS.md` (первая строка), `README.md` |
| вкладка браузера | `frontend/index.html` — там `<title>apptemplatepy</title>`. В общий поиск попадает, но в списке файлов выглядит разметкой и пропускается чаще прочего, а видит его каждый, кто открыл приложение |
| текст стартовой страницы | `frontend/src/routes/home.tsx` — заголовок «Стартовый шаблон на Python» и абзац под ним написаны про шаблон. Общий поиск их тоже не найдёт, а человек читает их на первом же экране своего приложения |

Глобальный `sed` сломает половину молча: одно и то же слово в разных файлах
значит разное, и часть вхождений менять нельзя.

Чего трогать **не надо**:

- `app-template-ts` в комментариях `backend/app/core/security.py`,
  `backend/app/core/rate_limit.py` и `backend/app/features/users/schemas.py` —
  это ссылки на соседний шаблон, а не имя этого приложения.
- Имя куки сессии: `AUTH_COOKIE = "app_session"` в
  `backend/app/core/security.py` слага не содержит, и приложения на сервере
  разведены по доменам.
- В `README.md` смысл различается **внутри одного файла**: заголовок — это
  имя приложения и подлежит замене, а `git clone …/webkoth/app-template-py`
  и «установка из шаблона app-template-py» — имя репозитория-источника, его
  трогать нельзя. Читай каждое вхождение, а не файл целиком.

`.env` в таблице нет намеренно: на этом шаге его ещё не существует, он
появляется в шаге F копированием уже переименованного `.env.example`.

После правок прогони поиск ещё раз — `node scripts/onboarding-check.mjs`
покажет две строки: «переименование» и «текст стартовой страницы переписан».
Обе обязаны стать `OK`; если нет, скрипт назовёт оставшиеся файлы и
оставшиеся фразы. Вторая строка нужна отдельно потому, что слова
`apptemplatepy` в тексте страницы нет вовсе: общий поиск её не находит, а
человек читает её на первом же экране.

## E. Репозиторий

1. `git remote -v` — покажи, что origin сейчас указывает на шаблон.
2. Спроси адрес нового репозитория. Владелец создаёт его руками в профиле
   `webkoth` и даёт роль `admin` — без admin установка не сможет завести
   секреты Actions и ключ деплоя.
3. `git remote remove origin`
4. `git remote add origin <URL>`
5. `git push -u origin main`
6. Проверь права: `gh api repos/<владелец>/<репо> --jq .permissions.admin`
   должно вернуть `true`.

Если адреса ещё нет — оставь репозиторий без origin и скажи, что публикация
не настроена. Не открывай PR в шаблон.

## F. Первый запуск

Баз две: рабочая и отдельная под сквозные тесты. Отдельная обязательна —
прогон тестов сбрасывает схему целиком, и одна база на обе переменные
означала бы уничтоженную рабочую схему.

- Заведи роль и обе базы. **Роль обязательна, и она первая**: строка
  подключения в `.env.example` — это `postgresql://<слаг>:<слаг>@…`, то есть
  вход по роли с паролем, а не по имени пользователя системы. Без роли
  `make migrate` падает на `role "<слаг>" does not exist`, и ищут причину в
  миграциях, а не в пропущенной команде. Воспроизведено.
  - **macOS/Linux:**

    ```bash
    psql -d postgres -c "CREATE ROLE <слаг> LOGIN PASSWORD '<слаг>'"
    createdb -O <слаг> <слаг>_dev
    createdb -O <слаг> <слаг>_e2e
    ```

  - **Windows:** `psql -U postgres -c "CREATE ROLE <слаг> LOGIN PASSWORD '<слаг>';"`,
    затем `psql -U postgres -c "CREATE DATABASE <слаг>_dev OWNER <слаг>;"` и
    то же для `<слаг>_e2e`

  `-O` (и `OWNER`) задаёт владельца **при создании**. Отдельным
  `ALTER DATABASE … OWNER` это делать не надо: промахнувшись именем, легко
  сменить владельца чужой базы, и заметят это не сразу. Владелец нужен по
  делу, а не для порядка: обвязка тестов делает `DROP SCHEMA public CASCADE`
  в базе `_e2e`, и роль без владения этого не может.

  `CREATEDB` роли не нужен — базы создаёт суперпользователь командой выше.
  Право «заводить базы» приложению не требуется никогда, а на контуре роль
  и вовсе заводит провижинер.
- `cp .env.example .env`, подставь `DATABASE_URL` и `DATABASE_URL_E2E`,
  сгенерируй `APP_AUTH_SECRET`: `openssl rand -hex 32`.
  `APP_BOOTSTRAP_*` не трогай: пара всегда admin / admin.
- Проверь, что подставленная строка действительно работает, — до `make
  migrate`, а не после:

  ```bash
  psql "$(grep '^DATABASE_URL=' .env | sed 's/DATABASE_URL=//;s/"//g')" \
    -tAc 'SELECT current_user, current_database()'
  ```

  Ожидается `<слаг>|<слаг>_dev`. Другой ответ — опечатка в `.env` или
  пропущенная роль; здесь это одна строка, а через два шага — трейсбек
  asyncpg на пол-экрана.
- `make install`
- `make migrate`
- `cd frontend && npx playwright install chromium && cd ..`
- `make dev` — бэкенд поднимается на 8000, фронтенд на 5173 и проксирует к
  нему `/api`. Открой **http://localhost:5173**, войди парой admin / admin,
  покажи пользователю главную страницу и раздел «Расходы». Останови
  `make dev` (Ctrl+C).

  Именно `localhost`, а не `127.0.0.1`: Vite слушает имя, и на macOS оно
  разрешается в IPv6-адрес — замерено `lsof`, сокет один и он `[::1]:5173`.
  По `http://127.0.0.1:5173` браузер получает отказ соединения. Бэкенд, для
  сравнения, слушает `127.0.0.1:8000`, и прокси Vite идёт именно туда.
- `make check` — первый прогон на macOS долгий, см. предупреждение в шаге B.
- `node scripts/onboarding-check.mjs` — покажи таблицу.

## G. Ключ машины

```
ssh-keygen -t ed25519 -f ~/.ssh/<слаг>_ops -N "" -C "<слаг>-<имя>-<машина>"
```

Добавь в `~/.ssh/config`:

```
Host <слаг>-ops
    HostName 161.104.50.20
    User ops
    IdentityFile ~/.ssh/<слаг>_ops
```

Выведи публичный ключ (`~/.ssh/<слаг>_ops.pub`) с текстом: «Отправь этот
ключ владельцу — он даст доступ к серверу». Шаги H–J ждут этого; если ключ
ещё не добавлен, скажи об этом прямо и предложи вернуться позже.

## H. Контур

`ssh <слаг>-ops sudo app-provision <слаг>`

Скрипт сам выбирает порт, заводит базу, vhost, сертификат, cron резервных
копий и ops-скрипты. На выходе — адрес контура и публичный ключ репозитория.

Запиши адрес, порт и имя базы в раздел «Контур» файла `CHECKLIST.md`.

Если скрипт отказался из-за нехватки места или памяти — не обходи проверку.
Скажи владельцу: серверу нужно место, иначе новое приложение положит
соседние.

**`uv` на сервере — отдельный шаг.** `app-provision` общий с
`app-template-ts` и Python на сервер не ставит, а доставка вызывает `uv` от
пользователя `deploy`. Без него прогон падает уже ПОСЛЕ `git reset --hard`:
на контуре останется новый код при старом процессе. Убедись, что `uv` лежит
в `~deploy/.local/bin`, и поставь, если нет, — порядок в
`docs/superpowers/runbooks/server-setup.md`. Отметь в `CHECKLIST.md`.

## I. Автоматическая доставка

1. Публичный ключ из шага H — в репозиторий как read-only Deploy key:
   `gh repo deploy-key add <файл> --title "<слаг>-server"`
   (ключ можно сохранить во временный файл и удалить после).
2. `gh secret set SERVER_HOST --body "161.104.50.20"`
3. Приватный ключ Actions — конвейером, **не показывая на экране**:
   `ssh <слаг>-ops sudo app-deploy-key <слаг> | gh secret set DEPLOY_SSH_KEY`

## J. Первая доставка

`git push origin main` — если после шага E ничего не менялось, сделай пустой
коммит или доставь изменения переименования.

Дождись прогона: `sh scripts/wait-for-run.sh deploy.yml`

Скрипт ждёт прогон именно за этим коммитом и отказывается считать успехом
чужой. На первой доставке разница особенно велика: прогонов у нового
репозитория ещё нет вовсе, и прежняя подстановка `-L1` давала пустоту и
невнятный отказ самого `gh`.

Проверь контур: `curl -s -o /dev/null -w "%{http_code}" https://<слаг>.161.104.50.20.sslip.io`
Ответ 200 — контур жив. Приложение — SPA: неизвестный путь отдаёт
`index.html`, а на форму входа уводит роутер в браузере, поэтому переброса
кодом 307 здесь не бывает.

Первый вход на контуре — admin / admin.

Скажи прямо: контур открыт снаружи, а эта пара известна всем, у кого есть
шаблон. Под ней не работают — владелец заводит себе учётную запись в
разделе «Люди», входит под ней и отключает `admin`; после этого
`APP_BOOTSTRAP_*` убирают из `/var/www/<слаг>/.env`.

Именно завести и отключить, а не «сменить пароль»: смены пароля в
приложении нет. Пока вход идёт под дефолтной парой, на первом экране висит
предупреждение об этом — оно исчезнет само.

## K. Завершение

1. Удали блоки между `BOOTSTRAP_ONLY_START` и `BOOTSTRAP_ONLY_END` из
   `AGENTS.md` и `CLAUDE.md`.
2. В `CHECKLIST.md` поставь состояние `завершена ГГГГ-ММ-ДД` и отметь
   чек-листы «Проверки окружения» и «После установки».
3. Прогони `node scripts/onboarding-check.mjs` — всё должно быть OK.
4. Доставь это обычным `/ship`.
5. Скажи пользователю итог: адрес контура, его учётная запись, что осталось
   у владельца, и что работа над фичами начинается со слов «хочу сделать …».
