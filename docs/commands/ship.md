# /ship — доставить изменения на контур

Строго по шагам.

1. Проверь текущую ветку (`git branch --show-current`). Если это `main` с
   незакоммиченными изменениями фичи — сначала создай feature-ветку:
   `git switch -c feature/<короткий-слаг>`.
2. Если есть незакоммиченные изменения: прогони `make check`, исправь
   падения, затем закоммить (conventional commit, описание на русском).
   Поменялась схема API — `make openapi`, иначе `make check` упадёт на
   расхождении типов клиента.
   Есть новая миграция — доставка применит её на контуре сама
   (`alembic upgrade head` в конвейере). Деструктивную миграцию (удаление
   таблицы или колонки с данными) предупреди владельца ДО пуша: откат кода
   её не отменяет, спасает только резервная копия.
3. `git push -u origin feature/<ветка>` и дождись CI:
   `gh run watch $(gh run list --branch feature/<ветка> -L1 --json databaseId -q '.[0].databaseId') --exit-status`
4. `git fetch origin && git switch main && git pull origin main`
5. `git merge --no-ff feature/<ветка>` — конфликты решай по смыслу; если
   конфликт затрагивает чужую незнакомую логику, остановись и спроси.
6. `git push origin main`
7. Дождись доставки:
   `gh run watch $(gh run list --branch main -L1 --json databaseId -q '.[0].databaseId') --exit-status`
   Красный прогон — прочитай `gh run view --log-failed`, почини причину на
   feature-ветке и повтори с шага 2.
8. Удали слитую ветку (`git branch -d feature/<ветка>`) и назови
   пользователю адрес контура.

**Помни:** контур один, и он боевой. Проверки шага 2 и CI-гейт — всё, что
стоит между правкой и живыми людьми. Если после доставки что-то сломалось,
лечит `/rollback`.

**Запрещено:** пушить в `main` в обход merge с feature-ветки; отключать
проверки, чтобы «просто доехало».
